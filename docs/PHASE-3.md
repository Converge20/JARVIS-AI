# Phase 3 — OpenAI text intelligence, task tools and future British voice

Implemented on `feat/axiom-neural-interface`. No public deployment, merge, purchase, real API test call or microphone request is part of this change.

## Start without paid requests

In the existing repository, using Node 24 LTS (or Node 22.12+):

```bash
npm ci
cp .env.example .env
npm run dev
```

The combined runner starts a loopback-only Node API (3001) and Vite (5173). Both stop when the runner stops; a failed child stops the other. Vite proxies `/api` to the Node server. A missing key produces **Configuration required**; a key with `OPENAI_ENABLED=false` produces **AI disabled**. Neither state calls OpenAI. Tasks, navigation, anatomical rendering and manual visual demonstrations remain usable.

For a production build, run `npm run build` then `npm start`. The Node server serves both `dist/` and `/api` at `http://127.0.0.1:3001`. `npm run preview` previews only the frontend and is not the full assistant. There is no automatic deployment.

Never paste the key into this chat, source code, browser settings, a `VITE_*` variable or a terminal command that will be retained in history. An alternative is entering it directly in the ignored `.env` using the Codespaces editor. Never commit `.env`.
3. Keep `OPENAI_ENABLED=false` until you approve API usage against your own OpenAI project. This implementation does not create an account, purchase credit or activate billing. ## Data flow and task functions

Browser → same-origin `/api/chat` → official OpenAI SDK Responses API. Only the last 20 non-workspace conversation messages (24,000 total characters maximum), local date and current task snapshot (up to 200 tasks) are submitted. Browser requests never contain the API key. The server retains only bounded request IDs and usage counters, not conversation content. `store: false` disables Responses API object storage; this is **not** a promise of zero provider retention. OpenAI's API data policies still apply. Task context and chat leave the browser when you submit an enabled AI request.

The model has four strict function schemas:

- `list_tasks`: filters the supplied browser task snapshot; the backend submits the actual result to the model for its answer. This is local task retrieval, **not web search**.
- `create_task`: proposes a new title, priority and optional ISO due date. The browser's local date helps resolve “tomorrow”.
- `update_task`: proposes the full replacement fields of a known task, including completion and due date.
- `delete_task`: proposes deletion of one exact existing ID.

The backend validates all arguments and IDs. Only one tool operation is supported per message, with at most two SDK calls. There is no autonomous tool loop. Mutation tools return `awaiting_user_confirmation` to the model. The frontend displays current/proposed details and **Confirm task change / Cancel task change**. Nothing changes until confirmation. Explicit application functions revalidate the proposal against the latest task snapshot; stale edits/deletions fail instead of overwriting a newer change. Confirmation of creation is also required. The result is added to conversation context so later questions see the actual outcome.

Manual task editing and deletion now also ask for confirmation. Completion toggles remain direct. Optional `dueDate` extends the existing `jarvis.tasks.v1` format without invalidating old records; it appears in the task list and editor. No scheduled notification service is implied. Tasks stay in browser local storage; failed storage remains visibly session-only. Chat history and future voice preferences are session-only. Use **New conversation** to clear context or recover from the history-size limit.

## Usage and security safeguards

- Defaults: 6 chat requests/minute, 100 SDK calls per process, 800 output tokens per call. Configure `AXIOM_MAX_REQUESTS_PER_MINUTE`, `AXIOM_MAX_API_CALLS`, `AXIOM_MAX_OUTPUT_TOKENS`; maximum accepted values are 30, 1000 and 2000. A tool-assisted response consumes up to two calls. Counted attempts include failures.
- One in-flight request per server process, browser double-submit guard, repeated request-ID rejection, no automatic retries, SDK timeout and whole-turn abort deadline. Browser waiting is bounded too. A request that fails or is abandoned can still incur provider usage; there is no guarantee that abort cancels provider computation.
- Bounded JSON/body/history/task sizes, explicit role validation, strict tool schemas plus runtime validation, no executable model output, no broad CORS. POSTs require a matching Origin and reject cross-site browser requests. A forwarded HTTPS origin must be configured exactly. Keys and upstream error contents are never logged or returned to the browser.
- These are single-user, in-memory safeguards, not a billing ledger. Restarting the process resets counters. Do not expose this unauthenticated local server publicly or treat origin checks as authentication. Use authenticated private Codespaces access. Public/multi-user hosting would require authentication, persistent per-user limits and a separate security review.
- Monitor actual API spending and token usage in the [OpenAI usage dashboard](https://platform.openai.com/usage). Use a dedicated project with the minimum required key permissions; configure project budget alerts/limits where available. Budget alerts alone may not be a hard spending cap. No programmatic purchases or billing setup are included.

## Brain states and British voice

The existing anatomical meshes/materials/cortical paths, licensing and rendering optimisations are unchanged. Visuals illustrate app events and manual previews, never measured cognition.

| State               | Real trigger in Phase 3                                                                                          |
| ------------------- | ---------------------------------------------------------------------------------------------------------------- |
| Idle                | Default and after successful text responses/errors                                                               |
| Analyzing           | While awaiting the actual text request                                                                           |
| Task processing     | Local task changes, including confirmed AI mutations                                                             |
| Knowledge retrieval | Short acknowledgement when the server reports a completed real `list_tasks` tool; not live token-level telemetry |
| Listening           | Manual visual preview only; no actual microphone implementation                                                  |
| Responding          | Manual visual preview only; no actual speech output implementation                                               |

The backend is request/response rather than streaming, so retrieval activity is known when the final response arrives. General-knowledge answers use model knowledge, not internet retrieval. Manual Listening/Responding previews use the existing synthetic amplitude; live text responses do not activate those previews or the fake voice waveform. Future audio will require actual measured amplitude before driving those modes.

`src/services/voice.ts` defines a future push-to-talk/speech transport contract with transcript, phase and measured amplitude callbacks. It records `gpt-4o-mini-tts` as the planned synthesis API, supported synthetic voice IDs (`onyx`, `echo`, `fable`) and original British masculine voice instructions. Preferences allow a session-only future selection; no transport is implemented and no speech route is exposed. The accent, depth and delivery need listening validation in the next phase and are not guaranteed by a voice ID. No actor cloning or impersonation is requested. Real microphone consent, speech recognition, playback/mute controls and audio-driven brain activity remain planned.

## Validation and manual review

```bash
npm test          # React/services/anatomical assets + Node API/SDK mock tests
npm run build    # TypeScript and production bundle
npm run test:e2e # Chromium workflows and real WebGL rendering, no paid calls
```

All automated API responses use injected clients or the official SDK with an intercepted in-memory fetch. HTTP integration tests bind only loopback. Playwright explicitly disables OpenAI, clears the API key, uses a separate backend port (3002) and refuses to reuse an existing developer server. Stop any preview on 5173 before running browser tests. Browser AI workflow tests intercept `/api/chat` with labelled test fixtures. No real credentials are required or used. CI runs the same commands; software WebGL is a CI/browser-test setting only.

After approving and configuring your own API usage, manually try:

1. “Explain compound interest.” Follow with “Give me an example with £1,000.” Verify contextual replies and connection status.
2. “Create a task to study finance tomorrow.” Verify the date and confirm; refresh to check local persistence.
3. “Show me my outstanding assignments.” Verify the actual local tasks and retrieval acknowledgement.
4. “Mark my finance review task as complete.” If ambiguous, clarify. Verify the displayed change, then confirm.
5. “Delete my study finance task.” Cancel first; verify it survives. Ask again to confirm deletion.
6. Disable `OPENAI_ENABLED`, restart, and verify an explanatory error instead of a made-up answer. Test manual neural states independently; they remain labelled previews.

A live paid end-to-end conversation and voice quality cannot be claimed from mocked tests. No paid API validation was performed in this environment.
